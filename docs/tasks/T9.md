# T9 F2L 不允许前置 U

## 问题

`algSolvesCase` 对除 LSE 外的所有组都允许公式执行前先转 U（`pre` 取 0–3）。对 OLL/PLL/CMLL 这是 AUF，合理；但 F2L 的起始状态对 U 敏感（`src/lib/practice.ts` 开头的注释也这么说），先转 U 等于换了另一个情形。结果是一条“解的是 U 转动之后那个情形”的公式，会被当成这个情形的解。

原因正是 `pre = 1` 把开头的 `U'` 抵消掉了。构造没换，测试用的是第一条 F2L 情形。

## 改动

- `src/lib/cases.ts`：`algSolvesCase` 的前置 U 取值改成 F2L 只取 `[0]`，其余组仍是 `[0, 1, 2, 3]`。改了函数上方的注释，写明 F2L 只允许 post-U、不允许 pre-U，以及原因。
- LSE 自己的分支、`caseFingerprint`、`SET_RULES` 都没动。
- `src/lib/cases.test.ts`：新增两条测试，放在 `F2L 不允许前置 U` 里：定义公式 `algs[0]` 仍然能解决情形；`"U' " + algs[0]` 不能。

## 验证

- 红：见上。改实现后变绿。
- `npm test`：475 项全过（改前 473 项；新增 2 项，其中 1 项是“定义公式仍然成立”，所以不是预期的 474）。
- `npm run check:data`：367 项全过。已录入的 F2L 公式在 `pre = 0` 下都能解，没有需要停下来报告的情况。
- `npm run build`：通过。

## 后续风险

- 用户自定义的 F2L 公式如果依赖前置 U，保存时会被判成“解决不了这个情形”，只能强制保存，而强制保存的公式不会成为主公式（见 T10）。这是有意的后果：这类公式解的是另一个情形。
- 练习页答案区显示的是主公式，F2L 现在保证主公式在 `pre = 0` 下成立，答案不再需要先转 U。
- `caseFingerprint` 对 F2L 仍然把 U 前后调整当作同一情形，用来查重复录入，和这次的判定不是一回事，本次没扩范围。
